# 羲和模式运行手册（三档 × 半自动/全自动）

> 适用 `my-cumcm-deepseek` 的羲和运行。依据 `core/modes.js`、`core/agent.js`、`core/pool.js`、`core/project_plan.js`、`config/settings.json` 核对（2026-11-25）。宿主升级后重新核对；模型名、预算、并发数不写死，以当次配置与工具面为准。

## 0. 每轮先读模式，再动手

- 宿主每轮注入【当前协作模式：人机协同/全自动】与【当前深度：deep/extreme】；注入值优先于本技能的默认半自动，不因缺少文字约定切回半自动，也不要求用户重选；两者都缺失时按 `collab:fast`，不向用户复述设置。
- 术语对齐：本技能的“半自动”=宿主 `collab`（你拍板）；“自动”=宿主 `auto`（引擎按推荐项续推）。深度轴与协作轴正交，自动不等于高深度。
- 本技能不改档、不改 `settings.json`/凭据/全局模型。用户切档后按新档重排；已完成且未受影响的证据不重跑，受影响门禁标 STALE。
- 三档是加法不是替换：fast 的证据门禁在 deep/extreme 一条不少；反过来，高档位也不自动提高正确性，只提高检查密度。

## 1. 六种组合的实际差异

| 组合 | 子代理 | 重手法 | 决策卡 | 写盘/执行审批 | 推进方式 |
|---|---|---|---|---|---|
| 人机协同·fast（默认） | 无 `subagent_run` | 无 `deep_*` | 按题意 2–6 候选+自定义，等你选 | 每次写/跑/派活前批准 | 一轮一步，关键节点停 |
| 全自动·fast | 无 | 无 | 按题意 2–6 候选+自定义，引擎自动选推荐 | 完全访问 | 自动续推至完成 |
| 深度协同 | reviewer/worker 可用（派活需批准） | 辩论/方案树/回改循环/视觉闭环 | 按题意 2–6 候选+自定义，等你选 | 批准 | 高成本精做，分歧你拍板 |
| 深度全自动 | 可用 | 同上 | 按题意 2–6 候选+自定义，自动选推荐 | 完全访问 | 无人值守的高质量流程 |
| 极致协同 | 再加三固定职责、动态池、红队 | 继承 deep 全部 | 按题意 2–6 候选+自定义，等你选 | 批准 | 总师编排，人拍板 |
| 极致全自动 | 全部 | 全部 | 按题意 2–6 候选+自定义，自动选推荐 | 完全访问 | 无人值守全编制 |

- 比赛会话或全自动会话工具轮次上限 1500；普通人机协同非比赛会话 80；本地临时任务 18。轮次宽不等于可以空转。
- `fast` 隐藏 `subagent_run` 与四种 `deep_*`；`extreme` 才允许 `crew` 与 `redteam`。不可用的能力不假装调用。
- 全自动默认“完全访问”（用户未把 approval 显式改为 ask 时），它只是执行层不再逐次弹审批，不解除第 2 节的人不可代办项。

## 2. 所有档位共用的硬规则

- **证据口径**：只有 `formal:true` 的运行、正式结果表与门禁记录算数值证据；子代理报告、辩论共识、红队结论、自然语言“已验证”都不算。权威顺序：确定性检查器 > 辩论 > 子代理报告 > 主模型判断。
- **门禁照跑**：`conservation_check`（或 not_applicable+替代检验）、`repro_check`、`independent_verify`、`claim_trace`、`optimization_check`、`paper_build` 不因 fast 或自动模式省略。
- **决策卡条数**：羲和 `ask_user` 结构化卡支持 **2–6 个有依据候选 + 界面自定义**；按题意列，不足不硬凑，只有一个真实候选时改用普通 `options` 或纯文字确认。超过 6 个有意义候选：先在 `deep_tree`/工作记录全量登记，再取最相关 6 个入卡，并在淘汰理由中交代其余，不静默丢方法。
- **第三裁判**：`decision_judge` 只收恰好 3 候选做低风险初筛；卡片正好 3 个时可自动进入，2 个或 4–6 个的卡保留主模型推荐、不自动裁判；需要初筛时也可从卡内选 3 个显式调用。`auto_override:false`；高风险词、裁判不一致或低置信升级主脑/用户。裁判不替代授权，也不替你承担选错的责任。
- **预算**：以 `settings.json` 的 `daily_budget` 为准（当前核对值 200）。每次重手法前用一句话说明“为什么这里值得多花、预期拿回什么”；同一分歧只辩一次；预算熔断保留已完成部分，不从头重跑。
- **不可自动代办**：提交、外发/上传、删除原始题面与数据、修改宿主配置/凭据/全局模型、代替队员确认 AI 披露与人工核验。自动模式也不授权这些。
- **失败如实**：子代理超时、掉线、通道失败、工具缺失记“未执行/未返回”；主代理可接管修复，但不把未返回的报告记作通过。

## 3. fast 档：单主脑，基线优先

目标是用最短路径拿到能回答全部问题的可运行基线，证据齐全、可复现。

- 读题：`contract_register` 登记实体/边界/单位/目标/假设/规则等条款，`question_graph` 建问题表，`assumption_register` 只登记真实必要假设。
- 选路：无 `deep_tree` 时用一页纸比较目标、变量、数据需求、实现代价、翻车点与验证方式；按题意给 2–6 个有依据候选，不足不硬凑，只有一个时普通确认；主线外的只读调研和低成本可逆原型可先做。
- 求解：先最小基线再改进；长计算用 `job_start`→`job_wait`，不要轮询；`formal:true` 才进证据链；`spreadsheet_diff`/`result_compare` 做同口径互验。
- 验证：守恒/收支残差、复现门禁、口径与分母检查；`independent_verify` 只核清单哈希与口径，不能证明真实运行。自己另写一版算法可作替代实现，但必须披露“同一人、同假设、共享数据”，不称独立验证。
- 图：脚本出图后用 `vision_read` 自查轴、单位、图例、中文、裁切；fast 没有 `deep_visual` 的多轮闭环，关键图宁可少而准。
- 终审：R1/R2 双盲**未执行**（fast 无 `subagent_run`）。如实写“双盲未执行；主代理自查 + 可复现门禁”，不要用 `dispatch_child` 冒充双盲；若该工具实际可见且用户同意，也只算第三只眼。
- 何时建议升档：出现会改变主结论的方法分歧、优化不可行反复、图始终不合格、或时间允许更高质量检查时，向用户建议切 deep/extreme；不自行切档。

## 4. deep 档：四种重手法用在刀刃上

deep 继承 fast 全部规则；每用一种重手法先说清成本理由。

- `deep_tree`：开工选路或某问卡住时用。`expand` 列 2–6 个思路不同的候选（不固定条数），先基线、再按证据缺口和预算增补对照；`select` 写选择与淘汰理由；`result` 只认 formal 运行 stdout 的唯一 JSON 指标，并给出同口径 `comparison`（question/dataset/protocol/unit/direction）与对应 `measurement_key`（须与 err.value 一致），方向或定义冲突即拒。候选清单与选择理由进论文的模型选择说明。
- `deep_debate`：只用于真实分歧——两种方法结论差足以改主结论、关键数值没把握、评委会挑的地方。3 个立场不同的只读 reviewer 独立取证，裁判归纳；产出必须分“已收敛/仍存疑”，存疑落局限或假设表；与门禁冲突以门禁为准；同一分歧只辩一次，收敛后不再开第二轮。
- `deep_loop`：优化类或约束可行性反复失败时用。求解器报错原文回灌，模型改公式或实现，不静默改；每轮进 `iteration`；迭代轮输出不构成数值证据，最终必须 formal 重跑并用 `optimization_check` 回代目标、约束和结论范围。
- `deep_visual`：正式图出图后逐图检查，FAIL 只改表现层，不改数值；每张正式图有一轮记录，或写明为何跳过；视觉 PASS 不等于数学正确或 PDF 排版通过。
- 子代理：reviewer/worker 可用；半自动下每次派活需批准（除非已授权），全自动下不弹审批但仍受预算与边界约束；禁止嵌套派活；reviewer 工具层只读，路径范围靠任务说明和主代理复核。
- **R1/R2 双盲**：两个 `subagent_run(profile:"reviewer")`。R1 只看论文与图，R2 只看代码、结果、日志；任务里写清范围，互不通气、不给对方结论，各自先立检查标准。主代理按实际文件与门禁交叉核对冲突。任一未返回→“双盲未完成（R? 未返回）”，不补写成通过。
- 自动（auto:deep）：重手法同样先写成本理由；决策卡仍要出，引擎自动选推荐；不为“自动”而多开辩论。

## 5. extreme 档：三固定职责、动态池、红队

主代理是总师：编排、验收、汇总，不重复子代理的大段求解；子代理失败或容量不足时接管修复，只给最终文件和实际覆盖范围背书。

- **CREW**（`subagent_run(profile:"worker", crew:...)`，仅 extreme）：
  - `modeler` 只登记 `model_spec`/公式/假设/契约/问题表，不写代码；
  - `coder` 只按主代理给的规格写代码，不改公式；规格有问题回报告；正式结果 `formal:true` + `model_spec_id` + `uses_formulas`；
  - `writer` 只写主代理标为 committed 的问题，每个数值有 formal 运行或结果表背书；不改公式、不改代码；
  - writer 与 modeler 的 Python 只读，coder 可写；工具白名单由执行层强制，不靠提示词。
- **动态池**：只对独立路线、高风险假设或专项核查开池（`tasks=[{crew,prompt,why}]`）；最多 3 并发、每局 12 个硬上限；连续两轮无新缺陷/新路径就收敛；预算紧张先收敛，不为凑数量派活。
- **红队**：仅 extreme。只写 `findings/redteam/`；探针两段式落脚本并实际运行，`exit≠0`=攻击成功/结论被证伪，`exit=0`=守住；`report.json` 的退出码必须与引擎实际输出一致。红队结论不是主证据，主代理决定改结论、降主张还是补实验。
- **审阅层**：R1/R2 照做；可另派专项 reviewer 做 R3 文码一致、R5 时点因果、R6 精度量级、R7 诚实收束，但都只读、互不通气、报告需主代理核。
- **最小充分**：增加模型、特征、融合、代理或图表前，写明哪个题目要求或已证实缺陷尚未解决、简单基线为何不足、预期验证与预算；无可验证收益就回归简单方案，负面对照留档。

## 6. 半自动与全自动的操作差异

**半自动（collab）**

- 按题意给 2–6 个有依据候选的卡等你选；未选不推进该正式主线。只有一个真实候选时用普通确认。主线外的只读研究、低成本可逆实验可以先做。
- `fs_write`/`fs_edit`/`python_run`/`shell_run`/`subagent_run`/`support_pack` 等每次弹审批；同类小写入批处理，并用一句话说明要写什么、影响哪里；不自行选择“本会话总是允许”。
- 派子代理前告知目的、权限和预期成本；R1/R2 冲突、红队证伪、预算将尽先报给你。
- 每个已授权单元做完直接进入下一步，不反复问“继续”；不把沉默、预选或超时当授权。

**全自动（auto）**

- 关键选择仍要 `ask_user`：按题意给 2–6 个有依据候选，不足不硬凑，只有一个真实候选时用普通确认；引擎自动选推荐并继续。确实没有可列候选时，按自己的推荐决定并在契约/备注留痕，不空等。推荐项必须是你愿意为之负责的方案：`recommendation_reason` 比较各候选对题目、数据、赛时的适合度，记录选择、风险与回滚点。
- 执行层默认完全访问；`dispatch_external` 在自动模式会被跳过，需要外部模型时留人工项。提交、外发、删原始数据仍然不做。
- 逐问 commit 后立即进入下一问；剩余时间或预算不足时，迭代卡推荐“停止迭代并冻结”，不硬撑。
- 完成时回复【全流程完成】+ 产物清单；未做的人工核验、未取得的提交回执单列，不写成已完成。
- 自动不是免检：公式、守恒、复现、claim、PDF 逐页检查照旧。

## 7. 阶段 × 档位

- **baseline**：三档都先跑通基线；deep 只在这里用一次 `deep_tree` 选路；extreme 先 modeler→coder 跑通第一问再开池，writer 只写已 committed 内容。
- **iterate**：fast 单线按证据逐圈；deep 用辩论/回改循环处理真实分歧；extreme 可对独立实验开小池。所有档位都先 `iteration({op:"plan"})` 预登记判据，结果出来不回头改判据。
- **freeze**：禁止探索性换模型；deep 只做冲突裁决与正式图视觉检查；extreme 用红队攻关键主张；R1/R2 在结果冻结后终审。上游改动先传播下游失效，再重验。
- **final**：不引入新模型；`paper_build`、`support_pack`、`release_freeze` 按当届规则；人工核验与提交状态单列。
- 用户切档不重写历史证据，但受影响门禁标 STALE 重审；不因升档把旧结论自动升级为“已验证”。

## 8. 失败与降级

| 情况 | 处理 |
|---|---|
| fast 无子代理 | 走单主脑流程，双盲终审标未执行；可用 `dispatch_child` 时也只作辅助，不冒充双盲 |
| deep 工具不可用/超时 | 记录失败原因与轮次，回退 fast 等价检查；失败轮不作证据 |
| 子代理未返回/掉线 | 主线接管必要修复；报告标“未返回”，不记通过 |
| reviewer 写入被拒 | 正常现象（只读守卫）；改为读文件/跑只读 Python，或由主代理落盘 |
| 动态池额度/并发受限 | 收敛任务、串行关键路径；不伪造并发结果 |
| 全自动无人应答 | 按推荐推进并留痕；涉及人不可代办项时停在交付前，列待办 |
| 预算熔断/通道失败 | 停在首个未完成环节，保留已完成证据，恢复后从该环节续跑 |

## 9. 开局自检与收尾

开局六问：① 当前 effort/collab 是什么？② `subagent_run`/`deep_*`/`crew`/`redteam` 实际可见吗？③ 本轮范围与既有授权是什么？④ 哪些动作必须人确认？⑤ 时间与预算余量？⑥ 失败时降到哪条路径？

收尾报告：模式与档位；实际用了哪些档位能力（子代理/重手法/池/红队）；未执行项及原因（双盲、红队、人工核验、提交）；证据与产物路径；下一动作。不得把“档位开启”写成“检查已通过”。
