# 羲和 Agent 适配（妈妈杯）

专属入口 `my-mathorcup-bigdata` 的羲和安装副本。羲和是**双模型角色分工 + 主/子智能体 + 技能槽位**的宿主；本文件把妈妈杯大数据流程映射到羲和实际机制。模型名/端点以 `config/settings.json` 的 `role_models` 为准，**不硬编码模型名**，按角色名调用。三档 × 半自动/全自动的运行方式见 [羲和模式运行手册](羲和模式运行手册.md)，本文件只写机制映射。核对日期 2026-11-25。

Codex 版保持宿主中立；本副本多出本文件与 `skill-contract.json`，其余流程、参考和模板与 Codex 版同源。两副本不互相依赖。

## 1. 双模型角色分工

- `role_models` 四角色：**modeler/reviewer**（主脑/审查）+ **coder/writer**（编程/论文）；路由与回退由 `core/model_roles.js` 解析，显式会话选择不被静默回退。
- 阶段映射：题目契约、数据可解性、规则核验、复算审查、终审 → modeler/reviewer；清洗/特征/基线/主解代码 → coder；论文与摘要 → writer。
- 第三裁判 `decision_judge`（只收**恰好 3 候选**）：羲和结构化决策卡支持 **2–6 个有依据候选 + 界面自定义**，按题意列，不足不硬凑，只有一个真实候选时改用普通 `options` 或纯文字确认；超过 6 个先在 `deep_tree`/工作记录全量登记，再取最相关 6 个入卡并交代淘汰理由，不静默丢方法。卡片正好 3 个时可自动进入裁判层，2 个或 4–6 个的卡保留主模型推荐、不自动裁判；需要初筛时也可从卡内选 3 个显式调用。高风险词、裁判不一致或低置信 → 升级主脑或用户；`auto_override:false`，裁判不自动改推荐，也不替代半自动授权。

## 2. 主/子智能体

- `subagent_run` / `dispatch_child`：独立调角色模型、工具白名单、共享工作区；worker 可读写，reviewer 与 crew 的 modeler/writer 为 `pyMode:'ro'` 只读，红队只许写 `findings/redteam/`；禁嵌套派活。
- **R1/R2 双盲终审**（见 SKILL.md 七条补强第 4 条）：两个 `subagent_run(profile:"reviewer")`，R1 在任务里限定只看论文与图、R2 限定只看代码/结果/日志；工具层只保证只读（`pyMode:'ro'`），不按路径白名单，范围靠任务说明与主代理复核；互不通气、不给对方结论。R2 是审阅，独立复算另按“不读目标答案、不复用主解内核”执行并分开记状态。fast 无 `subagent_run` 时标"双盲终审未执行"。
- 档位：协作轴 `collab/auto` × 强度轴 `fast/deep/extreme` 共六种组合，未设置时按 `collab:fast`。**fast 隐藏 `subagent_run` 与 `deep_*`**；deep 解锁辩论/方案树/回改循环/视觉闭环；extreme 再解锁 CREW 三固定职责、动态池（3 并发/12 上限）与 redteam。比赛会话工具轮次 1500；全自动默认完全访问但 `dispatch_external` 被跳过。逐档操作、成本纪律与失败降级见 [羲和模式运行手册](羲和模式运行手册.md)。

## 3. 技能槽位与模板/插件

- `skill-contract.json` 声明 `slots: research/figures/review`、`modes: append/replace`；主槽 main 为妈妈杯主控。
  - **research**：资料库检索与同类论文蒸馏（`mathmodel-resources`）、方法文献核验（`academic-search`）。
  - **figures**：接 `plugins/evidence-figures`。选图按 [竞赛图表选型与视觉升级](竞赛图表选型与视觉升级.md)，把要回答的问题、冻结结果路径、统计口径、面板尺度、导出尺寸交给绘图阶段；槽位或插件不可用时用本机代码出图。
  - **review**：`bzd-*` 分章检查与终审技能。
- **论文模板**：`assets/paper-2026.tex` 是骨架，不是完成稿。复制到项目论文目录再改，不改 assets 原件；先核当届赛道规则。
- **规则审计与提交**：羲和用 `contest_rules` 登记已读来源与条款，`paper_build` 按当前规则审计，`support_pack`/`release_freeze` 生成并冻结提交包；未见提交回执不得称已提交。

## 4. 门禁工具

- `core/candidate_comparison.js`（由 iteration/deep_tree 调用，非独立工具）：对照实验只认 formal 运行 stdout 的唯一 JSON 指标，须声明同口径；双口径按事件口径/报告口径分开。
- 机理检验与复算：`conservation_check`（守恒/收支残差）、`independent_verify`（双方法/独立重算）、`repro_check`；公式 `formula_register`；规格 `model_spec`；主张—证据 `claim_trace`；优化 `optimization_check`。
- `python_run` 禁网/禁子进程，`formal:true` 才成证据；`core/blind_evaluation.js` 只做封存账本（非独立工具），要求人工评阅，报告恒为未执行自动盲评。

## 5. 工具面与降级

- 约 60 工具（fs_*、shell_run、python_run、job_*、kb_*、skill_load、vision_read、web_search/fetch、academic_search、subagent_run/dispatch_child、paper_build/support_pack/release_freeze 等）。只有实际暴露且调用成功的工具才算可用。
- references 按需 `skill_load`，不一次全读；每轮先看宿主注入的协作模式与深度档位，再探测 `subagent_run`/`deep_*`/`crew`/`redteam` 是否实际可见；缺失时记录并降级为串行最低流程，不模拟多代理、不改宿主配置与凭据、不自行切档。
- 断点恢复按 [宿主路由与断点恢复](runtime.md) 的清单核对权威入口、哈希与进程身份，再决定续跑或局部重跑。
